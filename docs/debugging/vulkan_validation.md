# Vulkan validation layers

**Reach for this first on any crash, hang, or "the GPU is doing something inexplicable."**
Reading code first is usually the slower path.

## Why it works

Vulkan drivers do essentially no error checking. `vkAcquireNextImageKHR` takes a
`VkSwapchainKHR` — an opaque 64-bit handle — and dereferences it on trust. Pass a destroyed
one and the segfault happens *inside Mesa*, with a backtrace that points at the driver rather
than at the mistake. The crash site and the bug site are in different libraries.

The Khronos validation layer sits between the application and the driver, checks every call
against the spec, and tracks the lifetime of every object. When a handle is not in its
registry it says so, by name, at the call that used it.

## Running it

```bash
cargo build --profile demo --example 10_present_timing_internals
VK_LOADER_LAYERS_ENABLE='*validation' \
  ./target/demo/examples/10_present_timing_internals buffered
```

No rebuild and no code change — the Vulkan **loader** injects the layer beneath the
application. VSE never requests it.

If the variable does not take (behavior varies by loader version), the fallbacks are
`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`, or temporarily adding
`enabled_layers: vec!["VK_LAYER_KHRONOS_validation".into()]` to the `InstanceCreateInfo` in
`src/core/device.rs`.

The layer is installed on the reference machine at
`/usr/share/vulkan/explicit_layer.d/VkLayer_khronos_validation.json`. On a machine without it,
install the Vulkan SDK or the distro's validation-layers package.

Output goes to **stderr**, interleaved with tracing output. Pipe to a file and grep:

```bash
VK_LOADER_LAYERS_ENABLE='*validation' ./target/demo/examples/... > run.log 2>&1
grep "Validation Error" run.log | sort | uniq -c
```

## Reading the output

Each error names a **VUID** — a valid-usage ID, a stable identifier for one spec rule, which
you can search in the Vulkan spec verbatim.

```
Validation Error: [ VUID-vkAcquireNextImageKHR-swapchain-parameter ]
vkAcquireNextImageKHR(): swapchain Invalid VkSwapchainKHR Object 0x20000000002.
```

Two habits make these far more useful:

- **Compare handle values across the log.** In the case above, the swapchain created most
  recently was `0x420000000042` while the acquire used `0x20000000002`. Two different objects
  is the entire diagnosis — a stale handle, use-after-free.
- **Count occurrences, don't just read the first.** `sort | uniq -c` separates "happens once at
  init" from "happens every frame," which usually distinguishes a setup bug from a hot-path bug.

## Worked example: the stale-swapchain use-after-free

`run_buffered()` segfaulted a few frames in, reproducibly, and had done so for several commits.
Four plausible hypotheses had been written up from code reading; none was correct. The layer
named it on the first run: an acquire against a swapchain that had been destroyed by the
recreation twenty lines earlier in the same function. Fixed in `2ef71dd`.

The lesson generalizes: **the hypotheses generated by reading Vulkan code are unusually
unreliable**, because the failure surfaces far from the cause. Get the layer's answer first,
then read code to understand it.

### Resolved: the missing present-timing swapchain bit (2026-08-03)

Two VUIDs used to fire from one cause — VSE created its swapchain without
`VK_SWAPCHAIN_CREATE_PRESENT_TIMING_BIT_EXT` while calling present-timing entry points on it:

```
20 × VUID-VkPresentTimingsInfoEXT-pSwapchains-12234
 4 × VUID-vkSetSwapchainPresentTimingQueueSizeEXT-swapchain-12229
```

Fixed by setting the bit (`pt::SwapchainOptIns`, composed in `src/core/swapchain.rs`). Three things
worth keeping from that investigation:

- **These VUIDs were the root cause of a documented "driver bug."** The earlier clock documentation had recorded ANV as stubbing `IMAGE_FIRST_PIXEL_OUT` to 0. It wasn't: the swapchain had never
  opted into timing, so there was nothing to report. With the bit set, `IMAGE_FIRST_PIXEL_OUT` goes
  **0/200 → 200/200**, deterministically, across nine alternating paired runs. A validation error
  dismissed as "spec pedantry, it works anyway" was the whole explanation.
- **The example's own summary line was actively misleading.** It reported
  `IMAGE_FIRST_PIXEL_OUT: true` off an `Option::is_some()` test, which is `true` for a reported
  stage carrying `time == 0` — it read "true" on exactly the condition it existed to detect, and
  printed `PASS ✔ scanout feedback all working` while the library simultaneously warned the
  timestamps were stubbed. Validation layers find *API misuse*; they cannot tell you your instrument
  asserts the wrong predicate. Check what a diagnostic actually measures before trusting a run —
  and when a diagnostic and the library disagree, that contradiction is the bug.
- **Establish the control before changing anything.** The fix looked like it had failed at first:
  the fixed build read 0/200 for several minutes because *the screen had blanked on the idle timer*,
  and a dark panel produces no scanout to timestamp. Only back-to-back alternating A/B runs of both
  binaries separated the signal from the environment. See `docs/timing-conformance.md#reference-path-measurements`.

## The timing caveat — read this before recording anything

The layer intercepts every Vulkan call. That overhead is real and it lands squarely on the
presentation path. In one paired 200-frame comparison on the reference machine, missed frames
went from 10 without the layer to 20 with it. That is a single pair and not a careful
measurement, but the direction is exactly what the mechanism predicts.

**A session recorded with validation active is not valid timing data.** Use the layer to find
bugs, then turn it off and re-record.

Because the loader injects forced layers beneath the application, VSE cannot detect this
through `Instance::enabled_layers()` — vulkano reports what was *requested*, and VSE requests
nothing. So the environment variables are captured into the host snapshot instead
(`HostInfo.runtime.env_vk_loader_layers_enable` and `.env_vk_instance_layers`), and
`HostInfo`'s `Display` prints a loud warning line when either is set. A non-`None` value there
disqualifies the run for timing analysis.

Note the asymmetry: a *recorded* value proves the run was instrumented, but `None` on an old
recording only means the fields did not exist yet — it is not proof of a clean run.

## What it cannot find

The layer checks conformance to the spec. It will not find logic errors that are perfectly
legal Vulkan: the wrong pixels, a stimulus drawn at the wrong coordinates, a flip scheduled
against the wrong deadline. For those, see `tests/headless_pixels.rs` (pixel-exact rendering
assertions) and `docs/timing-conformance.md` (timing evidence and characterization).
